# Architecture

This document explains how OpenTTD Blueprint is put together and the
trade-offs behind each decision. See `docs/RESEARCH.md` for the upstream
facts these decisions are grounded in.

## Goals, in priority order

1. Safety — never lose or corrupt a user's existing configuration, saves, or
   unrelated content.
2. Reproducibility — the same profile + manifest version should produce the
   same gameplay setup every time, on both platforms.
3. Upstream compatibility — use OpenTTD's own supported mechanisms; no
   forking, patching, or scraping.
4. Simplicity — the smallest design that satisfies the above.
5. Cross-platform consistency — Linux and Windows consume identical profile
   data.
6. Maintainability.
7. Aesthetics.

## Manifest design

`profiles/<name>/content-manifest.json` is the single source of truth for
*what content is required*. Nothing else in the repository independently
lists NewGRF names or versions — installers, docs generation, and tests all
read this file. Schema: `profiles/schema/content-manifest.schema.json`.

Each entry records: `name`, `type` (`newgrf`|`game_script`|`ai`),
`content_id` (BaNaNaS content ID, hex string) or `source: "none"` with a
`reason` for deliberately-omitted candidates that are documented but not
installed, `required`, `version`, `version_policy` (`pinned` — v0.1.0 only
supports pinned), `license`, `project_url`, `order` (integer — load order
within its `type`), `parameters` (verbatim NewGRF parameter string, already
researched — never left at author defaults without review), `dependencies`,
`incompatibilities`, and `notes`.

Excluded/rejected alternatives (e.g. AXIS, ECS) are *not* in this file —
they're documented in `docs/MODS.md` "Deliberately excluded" instead, since
the manifest describes what to install, not what was considered.

## Profile design

`profiles/<name>/profile.json` holds everything that is *not* content
acquisition: display metadata, minimum OpenTTD version, and the gameplay
settings this profile wants to enforce (map size, starting year, CargoDist
distribution mode, vehicle behaviour, economy toggles). Schema:
`profiles/schema/profile.schema.json`.

`profiles/<name>/openttd.cfg.block` holds the literal `key = value` lines
that get injected into `openttd.cfg`, grouped by INI section, authored by a
human (not generated by the installer at profile-authoring time) so the
exact values are reviewable in a diff. The installer's job is to inject
this block, not to invent config syntax at runtime.

The `[newgrf]` block is the one exception to "fully pre-authored": per
`docs/RESEARCH.md` §3/§5, the filename OpenTTD expects on the left-hand
side of a `[newgrf]` line isn't knowable until the content is actually
downloaded (BaNaNaS ships each item as
`content_download/<type>/<content_id>-<slug>-<version>.tar`, and the
`.grf` filename inside is set by that NewGRF's own author, not by
BaNaNaS or by us). So `content-manifest.json`'s `order` and `parameters`
fields remain the reviewed, human-authored source of truth for *what* and
*in what order and with what parameters* — but the installer builds the
actual `[newgrf]` block at install time by listing each downloaded tar
(`tar -tf`, never executed, never extracted outside OpenTTD's own
directories) to resolve its real filename, then pairing that filename with
the manifest's pre-reviewed `parameters` string, in manifest `order`.
This is the one place config content is computed rather than shipped
literally, and it's computed from data that is itself reviewed
(order + parameters), not invented.

Keeping the "what values" question in reviewable profile files instead of
installer logic means a profile change is a data diff, and the installer
code stays identical across all future profiles.

## Config ownership: patch, don't replace

Rejected: regenerating a user's entire `openttd.cfg`. It would silently
discard resolution, hotkeys, network, and other settings the user has
tuned that have nothing to do with the profile.

Rejected: a fully separate launch profile (e.g. `-c` pointing at an
alternate config file) as the *default* mechanism. It would produce a
gameplay experience disconnected from the user's normal OpenTTD launch
(different hotkeys, different window layout, arguably a second "install"
to keep in sync) for no safety benefit over careful patching, and Steam's
launch options are the only place to inject `-c`, which most users won't
touch. It's noted in `docs/TROUBLESHOOTING.md` as a manual opt-out path for
anyone who wants total isolation.

**Chosen: patch only Blueprint-owned keys, inside a marked block.**

- Every key OpenTTD Blueprint writes is wrapped between
  `### BEGIN OPENTTD BLUEPRINT (profile: <name>) ###` and
  `### END OPENTTD BLUEPRINT ###` marker comments, one block per INI
  section that needs changes (e.g. one block inside `[difficulty]`, one
  inside `[linkgraph]`, one inside `[newgrf]`).
- On install, the installer parses `openttd.cfg` line-by-line, and for each
  target section either updates the existing marked block in place (if this
  is a re-run) or appends a new marked block just after the section header
  (first run). Lines outside marked blocks are copied through byte-for-byte.
- This makes the installer idempotent by construction: re-running it
  produces the same file, because "update the block between the markers"
  is a stable operation regardless of how many times it runs.
- `blueprint-state.json` (see below) records exactly which sections got a
  managed block, so `uninstall` can remove precisely those blocks — never a
  blind restore-from-backup unless the user asks for that explicitly.

## Ownership metadata: `blueprint-state.json`

Written to the OpenTTD user-data directory (next to `openttd.cfg`) after a
successful install. Records: Blueprint version, profile name + manifest
version installed, install timestamp, path to the config backup taken for
this install, the list of content items detected as already present before
install (untouched, never claimed as Blueprint's), and the list of content
items Blueprint itself added. No secrets — this file only ever contains
names, IDs, versions, and timestamps.

This is what makes `--verify` and `uninstall` precise instead of heuristic:
they read this file rather than re-deriving "what did we do" from scratch.

## Download mechanism

Full detail and rationale: `docs/RESEARCH.md` §3. Summary: OpenTTD's
console `content` command family (`content update` / `content state
[filter]` / `content select <id>` / `content download`) is the only
mechanism used — no BaNaNaS scraping, no unofficial mirrors. It's driven
non-interactively by launching `openttd -D -x` (dedicated server,
never-save-config) and writing the command sequence to its stdin,
interleaved with real-time waits, capturing output to a log the installer
can show on failure or in `--dry-run` (dry-run stops before actually
invoking this — see below).

Two behaviours only surfaced through live testing against the real
content server, not from documentation, and materially shaped this design
— see `docs/RESEARCH.md` §3 for the evidence:

- `content select` takes the *numeric* ID shown by `content state`, not
  BaNaNaS's stable hex content ID — so each install run has to look that
  numeric ID up freshly (it isn't stable across runs) rather than caching it.
- An **unfiltered** `content state` prints OpenTTD's entire catalog (tens
  of thousands of items) and, worse, was observed to sometimes leave the
  dedicated server too busy digesting that output to reliably process the
  `content select`/`content download` commands sent after it. `content
  state <filter>` narrows the listing to just matching names, which is
  both far faster and reliably lets subsequent commands through — so the
  installer issues one filtered `content state <item name>` per required
  item instead of one bulk unfiltered call.

`content download` only fetches files; it does not touch `openttd.cfg`.
The installer resolves each item's real `[newgrf]` filename afterwards by
listing the downloaded tar's contents (see "Profile design" above), and
only then patches `openttd.cfg`. This keeps content acquisition and config
mutation as separate, individually-verifiable steps, per "Transaction-like
installation" below.

A full first-time sync of 9 items has been observed to take several
minutes end to end (each filtered query's own round-trip varies from a
few seconds to tens of seconds) — the installer waits generously and
prints progress context rather than assuming this is fast.

## Backup strategy

Before the first write to `openttd.cfg` in a given run, copy it verbatim to
`backups/<timestamp>/openttd.cfg` (Linux: under the Blueprint-managed data
dir, see `docs/LINUX.md`; Windows: under `%LOCALAPPDATA%\OpenTTDBlueprint\`,
see `docs/WINDOWS.md`) alongside a `metadata.json` (date, detected OpenTTD
version, source config path, profile, installer version). If the config
doesn't change (no-op re-run — the marked blocks already match), no new
backup is created; the installer detects this by diffing the *intended*
patched output against the current file before writing anything.

Content directories are never backed up wholesale — only configuration is
backed up. Content is additive and individually identifiable (see below), so
there's nothing to roll back there beyond "don't delete it," which
`uninstall` respects by default.

## Additive content, never destructive cleanup

The installer only ever adds files under `newgrf/`, `ai/`, `game/` — it
never deletes or reorganises anything already present. `blueprint-state.json`
distinguishes "content that existed before this install" from "content
Blueprint added," so a future cleanup command (not in v0.1.0) could target
precisely the latter without guessing based on filenames.

## Linux/Windows abstraction

`scripts/common/` holds everything that operates purely on the manifest,
profile files, and an already-resolved set of paths: config-block
patching, backup creation/restore, verification logic, state-file
read/write. These are implemented once, in a form both installers can
drive — v0.1.0 implements this logic in POSIX-ish Bash
(`scripts/common/*.sh`, sourced by `install-linux.sh`) and in a parallel
PowerShell module (`scripts/common/*.psm1`) rather than a single shared
interpreter, per the "avoid a new language dependency" constraint (see
"Dependency minimisation" below) — but the *algorithm* (parse → patch
marked block → write → verify) is identical and any behavioural change
must be ported to both.

`scripts/linux/` and `scripts/windows/` hold only what genuinely differs:
path/environment detection (Steam library discovery, XDG vs
`%USERPROFILE%`), process invocation for driving OpenTTD's content
downloader, and platform-appropriate output formatting.

## Idempotency

Running either installer twice with no manifest/profile change must produce
byte-identical `openttd.cfg` after the first run and leave content
directories unchanged (already-present content is detected and skipped, not
re-downloaded). This falls directly out of the marked-block patching
strategy and content-presence checks — there is no separate "idempotency
mode," it's a property of how install and verify are implemented.

## Trust boundaries

- The installer never executes downloaded content as code — NewGRFs and
  Game Scripts are data files interpreted by OpenTTD itself, which is the
  same trust boundary a manual Online Content download would cross.
- The installer never requires elevated privileges (root/sudo,
  Administrator) in v0.1.0 — all target paths are user-writable
  (`~/.local/share/openttd`, `%USERPROFILE%\Documents\OpenTTD`).
- The installer never phones home, telemetry-reports, or requires network
  access beyond the documented OpenTTD content mechanism.

## Dependency minimisation

Linux: Bash + coreutils + `jq` (for manifest/state JSON parsing — the one
addition beyond "standard POSIX utilities"; justified because hand-rolled
JSON parsing in Bash is exactly the kind of brittle-parsing anti-pattern
the project philosophy warns against, and `jq` is a single, common,
auditable, non-networked binary, not a language runtime). Windows:
PowerShell 7+ only — `ConvertFrom-Json`/`ConvertTo-Json` are built in, so no
equivalent extra dependency is needed there.

No Python, Node.js, Docker, or Java anywhere in the installer path.
